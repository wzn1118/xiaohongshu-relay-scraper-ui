# 今天你投了吗？

“今天你投了吗？”服务于从小红书寻找实习和校招机会的学生，帮助他们把分散的招聘信息整理成可以判断、修改和发送的投递材料，并在收到面试通知后继续整理面经、准备面试。

## 1. 需求起点人物及目标用户说明

这个产品最早来自创作者自己的求职经历。当时它只是一个非常简陋的 UI，用来处理自己每天重复搜索岗位、核对信息和准备投递材料的问题。真正推动它逐渐形成现在样子的人，是创作者的一位朋友，更准确一点，是他的前任。她和创作者一样，会在小红书寻找实习机会、浏览经验帖、了解公司评价。创作者把平时自用的版本交给她以后，才逐渐发现，很多自己早已习惯的操作，对第一次接触产品的人并不自然。她每次在哪个环节停下来，下一版往往就从那里继续改。

![产品最初的抓取面板](docs/prd-assets/product-origin-ui.png)

*产品最初的抓取面板。搜索参数、Relay、定时任务和运行日志都摊在同一个窗口里，第一次使用的人要先弄懂一整套技术配置。*

目标用户是有相似经历的在校生和应届生。他们会从小红书寻找实习、校招补录或团队直招机会，也会在投递之后继续搜索面经和公司评价。他们需要持续完成投递与面试准备，同时为课程、实习和休息保留精力。每位用户都可以导入自己的简历和搜索词，沿用同一套处理流程。

## 2. 真实需要与具体使用场景说明

小红书上有很多分散的招聘帖子。在创作者实际看过的岗位中，大部分在 BOSS直聘和猎聘上没有对应信息；不少帖子由业务负责人、团队成员或招聘人员直接发布，简历可以通过邮箱或站内信直达用人团队，因此这些机会尤为珍贵。

一次投递往往从搜索栏开始。用户输入关键词，逐条打开帖子，从正文和图片里寻找岗位要求与邮箱，再根据岗位修改简历标题、挑选相关经历、撰写求职信。帖子没有公开邮箱时，还要重新组织一段站内信。按照创作者的实际记录，一天投递五六个岗位需要一到两个小时；应届生平均要经历八十到一百次投递，才可能得到一次面试机会。

最消耗人的情况发生在流程中段。简历标题已经改好，求职信写到一半，用户才发现帖子发布于半年前，招聘早已结束，发布者也很久没有登录。创作者对此最直接的感受是：“忙活到一半才发现帖子是半年前发的，连发布者的 IP 属地都已经消失了。”此前投入的时间随即落空。

招聘平台没有收录这批团队直招信息，收藏工具只能保存链接，通用写作工具又缺少原帖、图片和个人简历之间的联系。岗位时效、信息提取、经历匹配和文案准备仍由求职者反复完成，这正是产品需要处理的一段过程。

投递发出去以后，求职者很快会遇到下一件事：准备面试。此时用户又要回到小红书，组合公司名、岗位名和“面经”等关键词重新搜索。搜索结果里常常混着不同年份、不同岗位和不同面试轮次；有人把问题写在正文里，有人放在图片里，还有人把后续追问补在评论区。用户往往要打开十几篇帖子，自己记下哪些问题反复出现、哪些经验对应当前岗位。等真正开始复习时，刚才看过的内容又散回了十几个页面。

## 3. Agent 的核心能力与使用流程

用户输入关键词后，Agent 批量爬取岗位卡片，继续打开帖子并提取正文，通过 OCR 读取图片里的招聘信息，再整理发布时间、正文完整度、岗位职责、任职要求、工作地点和联系方式。用户先查看帖子是否近期、信息是否完整、投递入口是否清楚，再决定是否继续准备材料。

![当前岗位搜索任务界面](docs/prd-assets/current-job-search.png)

*当前岗位任务把关键词、时间范围、搜索排序和启动检查放在同一条流程里，采集开始前先确认帖子时效与运行条件。*

用户上传简历后，Agent 从教育经历、项目、技能和成果中提取个人背景，将岗位要求与真实经历逐项对应，再按照 Prompt 和 Spec 生成邮件、站内信或 Cover Letter。草稿中的经历和数字可以回到简历原文，用户继续修改标题、称呼、语气和重点。

发送前，页面完整展示收件人、主题、正文和附件。用户确认后，通过自己配置的 SMTP 发送邮件；帖子仅提供站内信入口时，页面会准备可复制的私信并保留原帖入口。正文、匹配依据、草稿版本和处理进度都会保存在本机，中途暂停后可以从已有进度继续。

非岗位内容模块来自她投递之后的自然行动。发现感兴趣的岗位以后，她还会继续搜索这家公司怎么样、面试一般会问什么、有没有人分享过相同岗位的经历。用户输入公司、岗位和面试轮次，Agent 批量取得相关面经，读取正文、图片和评论，再把分散的问题、面试轮次、答题线索和发布时间放进同一个任务。岗位投递与面经整理共享原帖读取、OCR、任务恢复和结果追溯能力，用户从投递进入面试准备时，可以沿着已经保存的公司与岗位继续处理。

当岗位和面经积累到几十条时，她开始问：“这里面哪些更适合我？”“哪些公司值得优先了解？”“今天我应该先申请哪几个？”重新翻阅每张卡片，整理时间又会回到用户身上。Data Copilot 因此加入当前任务：用户选择岗位正文、面经、评论和分析产物作为上下文，也可以附上自己的简历，再直接提出具体问题；回答会保留引用和原帖入口，后续追问继续沿用同一批资料。采集完成以后，用户可以继续筛选、比较、总结和排序，决定下一步先处理什么。

## 4. 目标用户的实际体验反馈

产品最早只有一个非常简陋的 UI。大部分功能改进来自创作者的一位朋友，更准确一点，是他的前任。她和创作者一样，会在小红书寻找实习机会、浏览经验帖、了解公司评价。最开始，创作者把自己平时使用的版本交给她体验，后来逐渐发现，很多自己已经习惯的操作，对第一次接触产品的人并不自然。她每次在哪个环节遇到困难，下一版往往就会围绕那个问题继续改。

### SMTP 配置：她想直接完成邮件投递，却完全不知道怎样配置

最早的邮件投递需要用户自行填写 SMTP 服务器、端口和授权码。她第一次看到这些配置时完全不知道应该从哪里开始，甚至不知道授权码应该在哪里获取。后来，SMTP 配置被完整整合进前端，页面会针对不同邮箱给出对应的服务器、端口和授权码提示，用户可以跟随页面说明完成邮箱连接。

![当前 SMTP 配置界面](docs/prd-assets/current-smtp-setup.png)

### 本地模型：她想使用 AI，却不知道中转站是什么

早期版本需要用户自行填写 API、中转地址和模型名称。她既不清楚这些参数应该从哪里获取，也觉得为了偶尔寻找实习持续购买中转服务成本偏高。后来，产品加入本地模型支持，可以自动识别已经安装的模型。用户完成选择后便能直接调用，也不用再理解 Base URL 和接口协议这些技术参数。

![当前本地模型与背景资料界面](docs/prd-assets/current-local-model.png)

### Relay：她想开始搜索岗位，却先卡在浏览器连接这一关

最初使用产品之前，用户需要手动准备 Relay，并完成浏览器连接配置。对创作者来说，这是一套早已习惯的操作；她第一次接触端口和连接地址时，却完全不知道下一步应该怎样处理。后来，Relay 的准备、安装和连接被整合进启动流程，能够自动完成的步骤都交给系统处理，让用户打开产品后尽快进入岗位搜索。

![当前 Relay 配置界面](docs/prd-assets/current-relay-setup.png)

### 一键爬取和一键续跑：她最关心“刚才搜到的内容还在不在”

实际使用过程中，采集任务可能因为网络波动、页面验证或状态异常发生中断。早期版本重新运行时很容易创建一个新任务。她遇到这种情况时根本不关心 checkpoint 或任务状态，开口问的就是：“那刚才已经跑出来的那些全白跑了吗？”后来，任务状态管理被重新设计，已经完成的进度会持续保存，页面也增加了一键续跑。现在任务中断以后，用户选择继续运行，系统会识别此前进度，并从对应位置接着处理。

![当前历史任务中的续跑入口](docs/prd-assets/current-task-resume.png)

### Data Copilot：结果越来越多以后，她开始问“我应该先看哪个”

采集能力逐渐完善以后，一次任务可以获得几十条甚至更多结果，新的问题很快出现了：结果虽然已经集中到一起，她仍然需要逐条查看和判断。她经常会问：“这里面哪些更适合我？”“哪些公司值得优先了解？”“今天我应该先申请哪几个？”基于这些反馈，产品加入 Data Copilot，让用户直接围绕已经采集的数据提问，由 AI 根据当前资料完成筛选、比较、总结和排序。采集结束后，用户可以继续进入判断环节，决定下一步优先处理什么。

![当前 Data Copilot 界面](docs/prd-assets/current-data-copilot.png)

### 非岗位模块：她找实习时，也会顺手了解公司、面试和各种经验信息

使用一段时间以后，她开始通过产品查询面试经验、公司评价、求职攻略和其他用户分享。发现一个感兴趣的岗位后，她经常继续搜索“这家公司怎么样”“面试一般会问什么”“有没有人分享过这个岗位的经历”。后来，这些非岗位内容逐步进入产品，让岗位发现、经验查询和公司了解留在同一套使用流程里。她偶尔也会拿这个功能搜索自己感兴趣的内容，比如她喜欢的长发男。这个小插曲让创作者意识到，当一个工具足够顺手时，用户会很自然地把自己的其他需求也带进来。

![当前非岗位研究任务界面](docs/prd-assets/current-non-job-research.png)

这些改动没有沿着一张提前规划的功能清单展开。很多功能最早都来自她使用过程中一句很普通的话：“这个应该怎么配置？”“刚才断了还能继续吗？”“这么多结果我应该先看哪个？”“我还想了解一下这家公司怎么样。”她遇到配置门槛，下一版就继续降低配置难度；她担心任务中断后丢失结果，产品就补上状态保存和续跑；她面对大量内容难以判断优先级，Data Copilot 就开始承担分析和筛选；她希望继续了解岗位之外的信息，内容研究范围也随之扩展。产品在这样一轮轮真实使用和反馈里，慢慢形成了现在的样子。

## 5. 根据用户反馈完成的验证或优化说明

上述反馈已经形成可操作的产品改动：邮箱连接从手动填写技术参数变成前端引导，本地模型可以被自动发现，Relay 进入统一启动流程，采集进度与任务状态持续保存，Data Copilot 可以读取当前任务数据，非岗位研究也沿用正文读取、OCR、任务恢复和结果追溯能力。用户从搜索岗位走到整理面经时，可以继续使用已经保存的公司、岗位和个人背景。

另一轮可复核运行发生在 2026 年 8 月 2 日。创作者使用自己的真实简历和 20 条真实招聘帖子完成测试，系统取得 20 条完整正文，整理出 20 张岗位卡，并为每个岗位准备邮件、站内信或 Cover Letter 草稿；17 条帖子取得精确发布时间，3 条使用估算时间，同时识别出 6 个明确联系人和 9 条投递路径。这轮运行走到了草稿和投递路径准备阶段，在线模型写作和招聘方视角复核没有开启，真实邮件发送、总耗时变化和面试结果也尚未进入记录。

这轮真实数据测试进一步推动了岗位时效、正文缺失和发送确认的调整。当前版本将发布时间、时间置信度、正文完整度和联系方式提前到列表与详情页，文案流程先对照岗位要求和简历，再选择真实相关经历，并在发送前完整展示收件人、主题、正文和附件。下一轮将邀请一名目标用户独立处理五到六个岗位，记录总耗时、旧帖淘汰时点、草稿修改次数和最终行动，继续验证文案口吻、实际节省时间和真实发送结果。

## 本地运行

运行环境为 Windows 11、Node.js 22+ 和 Python 3.11+。岗位采集需要可由 Relay 连接的浏览器，模型写作需要可访问的模型服务或本机模型运行时，邮件发送使用用户自己的 SMTP 配置。

```powershell
.\start-windows.cmd
```

默认地址：`http://127.0.0.1:4317`

首次打开后，依次检查运行环境、连接浏览器 Relay、配置模型、导入简历并确认个人事实。详细操作见 [用户指南](docs/USER_GUIDE.md)，完整产品要求见 [PRD](docs/PRD.md)。

## 开发与数据

```powershell
npm install
npm run typecheck
npm run build
npm test
```

前端位于 `src`，Node API 与任务处理位于 `server`，数据处理脚本位于 `scripts`，任务数据与导出文件默认保存在 `data`。简历、背景资料和任务记录留在本机，演示与提交材料会隐藏姓名、联系方式及其他敏感信息；涉及真实人物经历时，使用前取得本人同意。
