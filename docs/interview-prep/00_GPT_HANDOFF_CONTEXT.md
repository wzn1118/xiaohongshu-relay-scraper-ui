## 事实协议

回答项目问题时，为每个重要陈述选择以下前缀：

- [当前已核验]：来自当前文件或本轮 Git/目录盘点。
- [文档记录]：来自 README、设计文档或 dated acceptance report。
- [历史快照]：来自旧 commit、旧发布包或 phase clone。
- [工作区实验]：当前未提交/未跟踪代码。
- [外部来源]：remote 指向他人仓库，不宜直接当作原创成果。
- [待补证]：需要候选人补充个人贡献、运行记录或数据报告。

当用户要求简历、项目介绍或口述稿时，优先使用 [当前已核验]，其次使用明确标注日期的 [文档记录]。遇到精确数量时先询问来源，再决定是否保留。

## 全事实库入口

当问题要求“所有事实”或需要精确追问时，先加载[全项目事实百科索引](facts/README.md)，再按问题加载对应的 XHS、本地项目、公开仓库或跨项目文件。事实库额外区分 `HEAD`、`W`、`U`、`S`、`R`、`D`、`LIVE` 和 `EXT`，并维护[事实冲突登记表](facts/cross/04_FACT_SOURCE_CONFLICTS.md)。

机械清单用于定位路径、符号、脚本和配置；它们不是个人贡献证明。涉及当前状态时，优先引用带日期的工作区快照；涉及测试、性能、用户量或业务结果时，先检查是否存在本轮命令、日志或报告。

## 追问策略

1. 先让候选人用 60 秒说明问题、用户、方案、结果和个人职责。
2. 追问一条完整链路：输入、状态、存储、接口、失败、恢复、输出。
3. 追问一个真实故障：触发条件、可观测信号、根因、修复、回归测试。
4. 追问一个取舍：为什么 Node + Python、为什么 JSON + SQLite、为什么原生 HTTP、为什么 MCP 独立端口。
5. 追问个人贡献：哪些模块由候选人设计/实现/验证，哪些来自第三方或已有代码。
6. 追问指标：只接受有日期、命令、日志或报告的数字；没有证据就要求改成定性描述。
7. 追问下一步：模块拆分、跨语言契约、性能基准、观测和数据治理。

## 禁止的面试误区

- 把当前工作区未提交 Codex 扩展说成 v3.0 发布能力。
- 把外部 wechat/prompt 仓库说成原创项目。
- 把 dated acceptance report 的测试数字说成当前现场结果。
- 把 README 中的样例数据量说成个人业务增长指标。
- 只讲模型调用，不讲 evidence、schema、确定性 validator、人工门禁和审计。
- 只讲抓取速度，不讲安全验证 gate、登录态边界、隐私和恢复。

## 推荐模拟模式

### 轻量模式

每轮 5 题：1 个项目概览、2 个技术追问、1 个故障题、1 个反问候选人。每题等待候选人先答，再给出事实核验和改写建议。

### 深挖模式

围绕主项目连续 20 题，覆盖架构、状态机、SSE、MCP、AI 质量、批量邮件、CI/CD、隐私、性能和债务。每 5 题给一次结构化评分。

### 压力模式

面试官假设候选人夸大了指标或贡献，要求逐条给出文件路径、commit、命令或 dated report。没有证据时，自动将答案降级为“设计目标/本地原型/历史记录”。
