# 行为面试问答

以下回答是结构，不是事实声明。候选人应替换成真实时间、人员和结果。

## Q1：讲一次你处理模糊需求的经历

回答结构：先把“采集数据”拆成发现、补全、证据、判断和交付；与用户确认最小闭环；为每一段定义输入、状态和验收；先交单个草稿和人工确认，再扩展批量和 Copilot。

## Q2：讲一次失败或返工

回答结构：早期一次性脚本解释不了中断和重复；记录触发条件；把问题改写成状态、checkpoint 和 ledger；增加 deterministic fixture；承认实际恢复率还需要日志证明。

## Q3：如何与不同技术栈协作

回答结构：Node 和 Python 各自有清晰职责；先定义 JSON/event/checkpoint 契约；用 fake runner 验证协议；错误分类和日志字段统一；让双方能独立测试。

## Q4：你如何处理技术债务？

回答结构：不以“重写全部”为目标；先画边界，找高变更/高风险路径；补 contract test；按 bounded context 拆 route/controller/repository；用指标验证回归和维护成本。

## Q5：遇到意见不一致怎么办？

回答结构：把争论变成用户目标、风险和可测假设；先做小实验或 fixture；记录取舍和回滚方案；保留反方意见在 ADR 中。

## Q6：讲一次你发现自己判断错误

回答结构：最初把问题理解为抓取速度；观察到限流、登录和恢复成本更影响体验；调整优先级到安全验证 gate、checkpoint 和可见状态；用任务完成/恢复指标复核。

## Q7：如何保证工作可交接？

回答结构：README、架构图、运行命令、证据账本、状态/事件 schema 和故障手册；每个功能有最小 fixture；不把关键知识留在口头或个人目录。

## Q8：如何平衡交付与质量？

回答结构：分低风险草稿和高风险副作用；先交可编辑和可审计版本；发布前用 check、Mailpit、clean package smoke；把未完成扩展标成实验。

## Q9：讲一次你处理敏感数据的经历

回答结构：先列资产和边界；将 key/Cookie/profile 与任务产物分开；日志脱敏；发布包净化；本地 fixture 脱敏；确认删除/留存策略。

## Q10：你如何学习陌生领域？

回答结构：先读 README、入口、数据模型和测试；画输入/输出/失败链；找最小可运行 fixture；再阅读复杂模块。Hegel/Asteria 可作为领域迁移案例。

## Q11：如何说明个人贡献？

回答结构：按设计、实现、验证、发布四列列出；给出文件、commit、测试或 dated report；外部代码和团队工作明确分开；没有证据的部分改成参与/学习。

## Q12：面对强势追问如何保持可信？

回答结构：先给已确认事实，再指出来源等级；把目标/设计/历史报告分开；主动给出当前风险和补证命令；不为了数字漂亮而扩大结论。

## Q13：你最自豪的工程决策是什么？

回答结构：把“失败后从头跑”改成可恢复 workflow，因为它同时降低成本、重复请求和用户不确定性；说明数据模型、恢复路径和测试方式。

## Q14：你会如何改进自己做过的项目？

回答结构：拆大文件、加跨语言 contract、补性能/故障注入、统一观测、清理未提交扩展并建立 release boundary；按风险和收益排季度计划。

## Q15：你希望面试官继续追问什么？

回答结构：邀请对方从一个真实链路追问，例如“从用户点击开始，任务如何跨 Node/Python/Relay 产生可恢复产物”，这样能展示端到端理解。
