## 2. 目标架构

### 2.1 输入快照

每个岗位生成前固定保存以下快照，并写入 `profileSnapshotId`、`sourceHash` 和 `promptVersion`：

- 岗位正文、卡片标题、图片 OCR/alt 文本、发布时间和来源 URL。
- 抽取后的岗位标题、职责、任职要求、地点、实习时长、到岗要求、投递邮箱和正文中的标题规则。
- 候选人基础资料、简历附件摘要、项目/经历证据及其来源文件、页码或字段。
- 本次生成上下文：目标渠道、是否有真实附件、已选邮箱、岗位批次和人工修改记录。

### 2.2 结构化抽取

`ApplicationInfoAgent` 输出带证据的结构化对象，所有字段保留 `source_field`、`evidence`、`confidence` 和 `verification_status`。标题规则单独进入 `application_subject_rule`，不能混入经历或任职要求。

抽取器必须把以下内容分开：

1. 岗位职责：公司要候选人完成的工作。
2. 任职要求：公司筛选候选人的条件。
3. 投递协议：标题格式、邮箱、附件命名、地点、到岗和时长。
4. 评价信号：通过率、错误分布、人工复核时长、转化率等指标词。

### 2.3 证据与岗位映射

`FitEvidenceAgent` 不再只返回一组相关经历，而是返回岗位轴上的证据矩阵：

- `must_have`：有直接来源证据，允许写成“我做过”。
- `transferable`：有相邻证据，只能写迁移方法和边界。
- `to_validate`：简历没有证据，必须写成入职后的试做、验证或复盘计划。
- `unsupported`：不进入正文，不用技能列表冒充项目经历。

每条映射保存 `requirement_id`、`evidence_id`、匹配词、匹配分数和来源。教育、地点、每周天数、实习时长和邮箱不能被绑定为经历证据。

### 2.4 生成契约

高级模型只负责生成结构化 JSON，不直接决定是否发送：

```json
{
  "email_subject": "...",
  "greeting": "...",
  "email_body": "...",
  "cover_letter": "...",
  "used_evidence_ids": ["..."],
  "requirement_matches": ["..."],
  "recommended_resume": "...",
  "resume_reason": "...",
  "generation_mode": "codex_runtime",
  "prompt_version": "..."
}
```

生成顺序固定为：岗位结论 -> 最相关证据 -> 对每条职责的行动方法 -> 结果/指标边界 -> 到岗信息 -> 下一步沟通。技术栈只作为行动依据出现，不作为正文主体。

### 2.5 AI 产品岗位专用机制

标题、职责或正文命中 AI 产品、chatbot、大模型、Agent、模型训练或评测时，正文必须出现完整机制链：

`用户 query/反馈 -> 痛点与场景分类 -> 案例库/评测集 -> 策略优先级 -> 运营或产品动作 -> 指标观察 -> 验证/复盘 -> 回写迭代`

历史材料没有提供的指标只能写“入职后如何验证”，不能改写为既往成果。Asteria、数据到决策工作台、用户反馈监测等证据分别落在产品机制、用户洞察和运营验证轴上，避免只罗列项目名。

### 2.6 确定性后处理与质量门禁

模型输出后必须经过确定性后处理：

- 标题规则优先于模型自由发挥，字段缺失时从当前候选人快照补齐。
- 清除“招聘/招继任/申请/应聘”等噪声，保留原始标题用于审计。
- 邮件正文没有真实附件上下文时，不得写“简历随信附上”“见附件”。
- `cover_letter` 非空字符不少于 800，目标区间 900-1,200，上限 1,600。
- 每个岗位至少有一条职责对应的方法段；AI 产品岗位必须通过机制链检查。
- `used_evidence_ids` 必须存在于当前候选人证据快照；冲突事实进入人工复核。
- 失败记录写入 `content_quality`，不覆盖原始模型输出。

当前实现已经把门禁写入 `outreach.content_quality`：`cover_letter_length_pass`、`ai_product_mechanism_pass`、`attachment_claim_without_context`、`role_evidence_count` 和 `batch_ready`。

## 3. 批量投递流程

1. **采集**：完整岗位正文和申请协议进入不可变输入快照。
2. **解析**：标题规则、职责、要求、联系人和附件要求分别抽取。
3. **匹配**：建立岗位-证据矩阵，标记直接证据、迁移方法和待验证项。
4. **生成**：高级模型按版本化 prompt 输出结构化草稿。
5. **后处理**：确定性修复标题、清理误报、补齐候选人快照字段。
6. **质检**：运行长度、证据、AI 机制、附件一致性和联系人门禁。
7. **人工确认**：只审阅 `needs_review` 或存在冲突的记录；通过记录冻结内容哈希。
8. **预览**：绑定实际收件人、附件 ID、附件 SHA-256、草稿版本和质量报告。
9. **发送**：按批次幂等发送；单条失败暂停后续发送并保留状态。
10. **回写**：保存预览哈希、发送结果、人工修改和后续反馈，供下一轮 prompt 评估。

批量服务现已在预览前检查 `outreach.content_quality.batch_ready`。明确失败的记录返回 `APPLICATION_COPY_QUALITY_FAILED`，不会进入预览或发送；旧记录未带该字段时保持兼容，待迁移重生成。

## 4. 历史数据迁移与灰度

### P0：已完成

- 标题规则抽取、字段补齐、噪声清洗和主题解析。
- AI 产品机制提示词和确定性兜底。
- 证据句清洗，禁止将“候选人简历记载”变成“在某实习期间”。
- `content_quality` 记录和批量投递前置门禁。
- 真实数据全量回放脚本及目标 PDF 回放。

### P1：历史草稿重生成

- 对 2,653 条去重记录按岗位轴分批重生成，不直接覆盖旧版本。
- 每条记录保存 `oldDraftHash`、`newDraftHash`、`promptVersion` 和质量差异。
- 优先处理 AI 产品、产品运营、用户洞察、增长和明确写出标题规则的岗位。
- 先跑离线门禁，再让人工抽查每个岗位轴至少 20 条。

验收：求职信最低线通过率 >= 98%；AI 产品机制链通过率 >= 95%；附件误报为 0；岗位职责映射平均 >= 2 条；证据 ID 不存在率为 0。

### P2：小批量真实预览

- 每次最多 10 条，只做邮件预览，不发送。
- 检查收件人解析、主题、正文、附件命名、正文附件一致性和草稿版本哈希。
- 记录人工修改率、拒绝原因、标题重写率和质量门禁误报率。

验收：预览生成成功率 100%；收件人和附件绑定错误为 0；人工退回率 < 15%。

### P3：批量发送与反馈闭环

- 通过 P2 后再按 20-50 条批次发送，使用现有幂等键、发送间隔和未知投递人工核对状态机。
- 将人工修改归因到标题、证据、职责映射、语气、长度和附件六类，按周做 prompt 回归。
- 任何质量门禁回归都停止扩批，保留上一版可回滚草稿。

## 5. 验证边界

本次证据包括：现有 71 个结果文件的离线全量回放、目标 PDF 的确定性生成回放、Python/Node 单元测试和批量服务门禁测试。没有执行外部真实邮件发送，也没有把招聘方回复、面试结果或录用结果当作已验证指标。后续上线验收必须把离线生成、人工预览、实际发送和招聘结果分别统计。
