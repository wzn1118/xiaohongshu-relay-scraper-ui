## 一、项目描述：产品是什么

### 产品是什么

**小红书公开信息 AI 数据工作台**：面向求职投递、受众研究和内容决策的本地 AI 工作台，通过 Multi-Agent Workflow 与 AI Runtime 对小红书公开内容进行采集、结构化分析和证据校验，并由 Data Copilot 提供围绕任务数据的多轮协作，帮助用户基于证据完成判断与行动；CLI 作为兼容回退路径。

## 三、项目经历一：岗位发现到投递准备闭环

### 项目名称

**小红书实习岗位 AI 求职助手**

### 项目描述

面向实习求职者的 local-first AI Web 产品。用户从小红书搜索结果或岗位详情开始，采集公开岗位信息；AI 补全后的岗位上下文中提取职责和任职要求，读取用户简历事实并建立证据匹配，生成岗位定制私信、邮件和 Cover Letter，再经过雇主视角评审和质量门禁，最后由用户确认后复制、发送或导出。

### 背景

岗位信息分散在不同页面，用户需要手工复制和整理；岗位卡片摘要不能代替完整正文；AI 文案容易脱离候选人事实；长流程失败后重新执行成本高，用户也无法判断结果是否真的可用。

### 任务

把一个偏采集和脚本化的能力，产品化为一条可解释、可恢复、有人审的求职准备闭环，并定义“什么才算完成”。

### 行动

1. 在 PRD 中明确用户、主流程、8 个 Agent 阶段、状态机、数据契约、异常路径、非目标和发布门禁。
2. 将岗位正文、发布时间、职责、要求、申请方式、核心技能和证据拆成独立字段，禁止用卡片摘要冒充正文。
3. 引入候选人背景记忆、证据 span、结构化输出和雇主评审，让私信、邮件和 Cover Letter 都能回到事实依据。
4. 设计人工确认、质量评分、artifact 导出、发送前审批和发送审计，形成从生成到交付的闭环。
5. 对任务状态采用未采集、部分完成、已完成、失败、可恢复等状态，使用户能继续原任务而不是盲目重跑。

### 结果

- 形成从发现岗位到发送/导出的完整产品链路，覆盖岗位、候选人、AI、审核、交付和审计六类对象。
- PRD v1.6 已细化到 34 个 UI 模块和 14 个服务模块，具备可开发、可验收的边界。
- 定义了“完整正文或明确 partial、证据可追溯、质量达标、结果可导出”的业务完成标准。
- 输出支持 JSON、CSV、XLSX、Markdown 和 SHA-256 manifest，便于复核、交接和归档。

### 解决的困难

- **信息不完整**：用正文覆盖和 body completion ledger 区分卡片、正文、部分正文和最终完成。
- **AI 幻觉和泛化表达**：用候选人证据、引用校验、雇主评审和质量门禁限制无依据内容。
- **状态不可解释**：把“任务结束”拆为阶段状态、覆盖率、artifact、错误原因和下一步动作。
- **自动化风险过高**：将私信和邮件保留在人机协同链路，邮件发送增加 SMTP、质量门禁和人工审批。

### 取得的成绩

将产品从“能抓到内容”提升为“能判断内容是否完整、能解释 AI 输出、能恢复任务、能交付结果”的可验收工作台。该项目最适合体现 AI 产品经理的产品定义、复杂流程拆解、质量标准设计和跨端交付能力。

## 四、项目经历二：单帖 AI 受众与关系分析

### 项目名称

**单帖受众洞察与关系扩展 AI 工作台**

### 项目描述

针对单篇公开内容，分析评论、评论线程、用户及可选用户主页，输出带证据锚点的受众洞察、用户画像和关系扩展结果，并支持取消、续跑、历史版本、覆盖率、partial 状态和 artifact 下载。

### 背景

单个帖子下的评论、线程和用户信息分散，人工难以判断哪些评论代表真实受众、哪些用户值得进一步研究。采集中还会遇到安全验证、用户页打不开、批量接口失败、模型遗漏实体和长任务中断。

### 任务

把“对帖子做 AI 分析”的概念落成有范围、有证据、有版本、有恢复能力的产品功能，同时避免把局部成功误报为全部完成。

### 行动

1. 以 post、run、analysis version、comment、thread、user、evidence 和 artifact 建立数据模型。
2. 设计按评论、线程和用户拆分的覆盖率，区分已分析、跳过、失败、模型遗漏和待续跑。
3. 引入 evidence anchor、证据摘要、模型调用统计、token 估算、错误分类和严格 artifact 校验。
4. 支持原任务 checkpoint 续跑、单用户恢复、取消、版本隔离和 active/latest 结果保护。
5. 将“真实 Relay、真实 HTTP、重启恢复、三帖完成”等条件列为独立验收项，避免只凭静态测试宣布上线。

### 结果

一次真实隔离运行记录为：

- `7` 次模型调用；估算输入/输出/总 token 为 `11,903 / 4,743 / 16,646`；
- pipeline/elapsed 约为 `186,773 / 187,420 ms`；
- `4` 条评论中 `1` 条已分析、`3` 条因 `model_omitted_entity` 跳过；
- `3` 条线程、`2/2` 个用户完成分析、`6` 条证据被接受；
- 发生 `1` 次批量到单体恢复、`1` 次 synthesis evidence failure；
- `9` 个 artifact 通过 JSON/JSONL、身份、覆盖率、数量、证据、SHA 和 secret scan 校验；
- 结果状态为 `partial` 且可续跑，没有错误地覆盖 active/latest 结果。

另一次历史恢复过程中，评论从 `1719` 条补齐到 `3010` 条，用户从 `726` 个补齐到 `1124` 个，说明原任务 checkpoint 续跑确实带来了可量化的数据恢复结果。

### 解决的困难

- **评论、线程、用户三类对象覆盖率不一致**：用分对象 ledger 和可续跑状态表达真实覆盖。
- **模型遗漏实体或批量接口失败**：支持从批量请求降级为单体恢复，并记录失败原因。
- **部分结果污染最新结果**：用 run/version 和 active/latest 保护，partial 结果只作为可恢复历史保留。
- **公开数据分析边界模糊**：将范围限制为当前任务公开数据，不做敏感属性推断。

### 取得的成绩

把一个高不确定性的 AI 洞察能力变成可观测、可解释、可恢复的产品功能；既能展示模型分析结果，也能明确告诉用户哪些数据没有分析、为什么没有分析以及下一步如何续跑。该项目最适合体现 AI 产品经理的 AI 场景设计、数据产品思维、评估体系和异常体验设计。

## 五、项目经历三：长任务恢复与数据一致性

### 项目名称

**长流程采集恢复与任务状态治理**

### 项目描述

为岗位采集、正文补全、受众分析和关系扩展建立统一的任务、checkpoint、attempt、状态和 artifact 治理，确保任务中断后能够继续原工作，并且不会重复采集、覆盖有效结果或留下虚假的完成状态。

### 背景

浏览器会话、Relay、安全验证、限流、AI provider 和进程重启都会造成长任务中断。单纯“重新运行”会带来重复数据、状态污染、结果丢失和用户无法判断进度等问题。

### 任务

让恢复成为产品能力，而不是开发者手工操作；恢复必须保留原任务语义，区分原任务续跑和全新扩展尝试。

### 行动

1. 设计原 job、checkpoint、attempt、run、cursor 和 artifact 的关系，确保恢复沿用原任务上下文。
2. 将 source body backlog 与分析 ledger 分开，避免“正文未完成”被错误统计成“分析数量不足”。
3. 增加 pending、partial、complete、failed、resumable 等状态，配合 CAS/原子写入和过期状态清理。
4. 针对浏览器、安全验证和 AI provider 设置超时、取消、重试、单体降级和人工接管路径。
5. 将恢复后的持久化状态、数据库、导出文件和最新结果一起验收，而不是只看进程是否退出。

### 结果

- 历史专项验证中，安全验证超时问题修复后，受众采集测试为 `29 passed`；Python 测试为 `179 passed`；契约测试 `16/16`；JobManager 测试 `21/21`。
- 原任务恢复成功保留历史结果，并完成评论 `1719 -> 3010`、用户 `726 -> 1124` 的数据补齐。
- 形成“进程在线不等于采集完成”的产品判断标准：必须同时检查卡片/正文、数据库、artifact、coverage 和最新结果。

### 解决的困难

- **恢复重复执行**：使用原 job/checkpoint 和去重状态，避免新建无关任务。
- **新扩展和原任务混淆**：为 fresh expansion attempt 隔离状态，避免覆盖原结果。
- **内存状态和持久化状态不一致**：把数据库、JSON/JSONL、artifact 和 UI 状态纳入同一验收口径。
- **Relay 在线但没有真实数据**：把 tabs、card/note/export artifact 作为实际 readiness 证据。

### 取得的成绩

将“失败后重跑”升级成“按阶段恢复、可解释、可审计”的任务产品能力，降低了长任务的重复执行和数据污染风险。这一案例可重点体现 AI 产品经理在复杂状态机、可靠性产品和数据一致性上的能力。

## 六、项目经历四：AI Provider、Agent 编排与质量门禁

### 项目名称

**可配置 AI Runtime 与证据驱动的文案质量体系**

### 项目描述

为产品提供统一的 AI provider/session/model 配置和 8 阶段 Agent 编排，兼容不同模型调用方式，并通过证据、评分、结构化输出、失败恢复和发送前门禁控制 AI 结果质量。

### 背景

不同 provider 的接口形态、模型能力、上下文限制和失败方式不同；求职文案又涉及个人经历和发送风险，单纯接入一个聊天接口不能满足可控性、可追溯性和可交付性。

### 任务

建立模型无关但可解释的 AI 基础设施，让产品能切换 provider、发现模型、保存配置、限制输出，并在低质量结果时阻止直接发送。

### 行动

1. 统一 Responses、Chat Completions 和本地模型的 provider 适配，增加模型发现、配置校验、超时和输出上限。
2. 将 8 个 Agent 阶段拆开，分别约束输入、输出 schema、证据要求和失败处理。
3. 对候选人事实、岗位要求和生成文案建立 evidence span 校验，增加相关性、证据、表达、可信度和行动准备等质量维度。
4. 将低于默认 `90` 分的内容转入重写或人工处理，邮件发送必须经过质量门禁和用户确认。
5. 将 API key 保存在本地 session/config store，不返回前端、不写日志、不进入 artifact，并用测试和 secret scan 验证。

### 结果

- 历史基础设施验收完成 `39` 个 Node 测试、`32` 个 Python 测试和生产构建，并验证配置持久化不会返回 `apiKey`。
- AI Runtime 支持 `responses`、`chat_completions` 和本地模型路径，模型配置与运行统计可追踪。
- 当前工作树的前端生产构建已通过；当前 Node 测试为 `377/379`，剩余 2 个失败用例与答案修复和独立读取工具并行执行有关，尚未标记为全绿。

### 解决的困难

- **Provider 不一致**：通过统一 runtime 和适配层降低模型切换对业务层的影响。
- **输出不可控**：使用 schema、token/超时上限、证据校验和质量门禁。
- **凭据泄露风险**：采用本地存储、最小回传和 secret scan。
- **AI 生成后无法交付**：把审核、人工确认、附件和发送审计纳入完整产品链路。

### 取得的成绩

建立了从模型配置、Agent 编排到质量门禁的完整 AI 产品基础设施，使 AI 输出从“聊天结果”变成“有输入边界、有证据、有评分、有人工确认、有交付审计的业务结果”。

## 九、面试回答模板

针对每个项目都可以按以下顺序回答：

**背景**：用户原来的流程、业务痛点、为什么现有方案不够。
